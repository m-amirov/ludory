# Ludory Studio: безопасное применение и обновление профилей в существующих играх

Дата: 2026-10-24. Статус: **проект решения, ожидает утверждения владельца**.

## Цель

Дать владельцу существующей игры возможность явно выбрать профиль Ludory,
увидеть последствия до записи, применить его и впоследствии обновлять без
перезаписи пользовательского кода, ассетов и конфигураций. Сохранить текущую
поэтапную стратегию отделения CEOS и Starter Kit от Ludory.

## Изученное текущее состояние

- `@ludory/studio` имеет профили `web-game` и `narrative-game`, каталог
  статических шаблонов, CLI `profiles list/show`, `create`, `migrate`, `inspect`.
- `create` сохраняет `ludory.studio.json`: версии, хеши исходников каталога
  и созданных файлов. Это историческая квитанция, **не разрешение обновлять**
  `index.html`, `src/**` или другие созданные игрой файлы.
- `migrate` создаёт только `ludory.project.json` из проверяемой legacy-схемы
  и не переносит/не переписывает другие файлы.
- Starter Kit содержит отдельный ownership-aware updater со статусами
  `managed`, `project-owned`, `semantic-merge`, `new-project-seed`,
  `target-mapped`, `ephemeral`; для mature game защищает `src/**`, `public/**`,
  `game-spec.yaml`, `AGENTS.md`, SDK/runtime и другое.
- CEOS располагает своим механизмом adoption и профилями. Эти источники
  остаются самостоятельными до проверки совместимости по функциям.

## Рассмотренные подходы

1. **Выбран: ограниченное, проверяемое внедрение.** Профиль добавляется как
   собственная конфигурация Ludory. Обновляются только объекты, впервые
   созданные этим механизмом и подтверждённые его состоянием. Legacy
   CEOS/Starter Kit можно анализировать, но нельзя автоматически присваивать
   их файлы Ludory или обновлять их из нового каталога. Преимущества:
   небольшая зона риска, идемпотентность, отсутствие изменений runtime.
   Ограничение: это ещё не полная замена updater Starter Kit.
2. **Отложен: полный перенос updater Starter Kit/CEOS.** Перенос правил
   ownership, semantic merges, skills mapping и исполнения миграций для всех
   существующих игр. Требует отдельной поведенческой parity-матрицы,
   реальных фикстур зрелых игр и согласования конфликтов; без неё опасен.

## Функциональный контракт первого этапа

- `ludory profiles apply --project DIR --name ID [--catalog DIR] [--json]`
  формирует read-only план по умолчанию. Только `--apply` совершает изменения.
- `ludory profiles update --project DIR [--catalog DIR] [--json]` так же
  планирует обновление уже активного профиля; `--apply` выполняет его.
- `ludory profiles status --project DIR [--catalog DIR] [--json]` только
  читает состояние, показывает активную версию, версии каталога, drift,
  защищённые пути и причины `BLOCKED`/`CONFLICT`.
- Для `apply` обязательны существующий корректный `ludory.project.json`,
  явно названный профиль и совпадающий `engine`. Все target-платформы игры
  должны входить в список профиля. При несовпадении — `BLOCKED`, без
  предположений по содержимому проекта. Для Phaser/других engine допускается
  явный совместимый внешний каталог; текущие встроенные web-профили не
  переименовывать и не расширять молча.
- Активное назначение профиля — **декларативная конфигурация для следующих
  подсистем** (AI/Release/Runtime), а не утверждение, что эти подсистемы уже
  подключены или что проект прошёл платформенную сертификацию.
- Файлы игры и квитанция `ludory.studio.json` остаются неизменными.
  Непосредственный результат — новые файлы только в выделенном
  пространстве `.ludory/profiles/`: неизменяемая версия конфигурации и
  атомарно публикуемые ревизии активного профиля с историей.
- Профиль может обновляться **только на более высокую SemVer-версию** при
  неизменном ID. Изменение исходного SHA при той же версии, понижение
  версии или попытка переключить ID командой `update` — `CONFLICT`.
  Явное переключение профиля является отдельной будущей операцией.
- Для установленных игр из PR #3 можно выбрать профиль, указанный в
  `ludory.studio.json`, но receipt не означает автоматический захват
  владения файлами шаблона. Для перенесённых legacy игр планируема только
  эта безопасная декларативная привязка после отдельного `migrate`.

## Ownership, транзакция и восстановление

1. **Default deny.** Никогда не изменять `ludory.project.json`,
   `ludory.studio.json`, `AGENTS.md`, `game-spec.yaml`, `package.json`,
   `src/**`, `public/**`, `assets/**`, lockfiles, SDK, evidence, saves,
   права на ассеты или произвольные существующие пути. Не запускать hooks,
   `npm install`, сборку, публикацию и сторонний код из каталога.
2. Новый `.ludory/profiles/` должен отсутствовать либо иметь проверяемый
   корректный state текущей версии. Не присваивать существующий чужой
   профильный файл только по совпадению имени/содержимого.
3. При создании писать только эксклюзивно (`O_EXCL`, `O_NOFOLLOW` если есть),
   проверять компоненты пути на символические ссылки/junction, canonical
   root, identity каталога и fingerprint плана до действия. Запрещать
   traversal, hardlink-указатели вне проверяемого проекта и непроверенный
   конфликт каталогов. Планы сериализуемы и не содержат бинарных данных.
4. Конфигурации профиля адресуются SHA-256 в неизменяемых файлах.
   Первое назначение атомарно создаёт `active.json` эксклюзивной ссылкой;
   последующие версии публикуются как **неизменяемые нумерованные ревизии**
   в `revisions/` тоже эксклюзивной ссылкой. Активное состояние выводится
   из последней корректной последовательной ревизии. Это осознанная
   корректировка способа публикации: даже конкурентно заменённый
   `active.json` не может быть затёрт обновлением через rename.
   Старые snapshot-файлы и история сохраняются. Любой drift базиса
   блокирует обновление, даже если план был READY несколько секунд назад.
5. Если происходит ошибка, убрать **только ещё не подтверждённые и
   неизменённые собственные временные файлы**, не удаляя пользовательские
   замены. При неоднозначном rollback — fail closed с путём сохранённого
   объекта для ручного восстановления. В статусе явно показывать ошибки.
6. `IN_SYNC` — без записей; `READY` — доступно к применению;
   `BLOCKED`/`CONFLICT` — без изменений. `--json` возвращает машиночитаемые
   версии, операции, конфликты и хеши, без игровых секретов.

## Границы и следующие этапы

- Обновление файлов исходных шаблонов, кодовых адаптеров, runtime и CEOS
  skills **не входит в эту фазу**. Для них нужны ownership provenance
  на уровне каждого файла, правила ручного semantic merge, хранение базовой
  версии, откат и отдельные parity-gates по реальным проектам.
- Установленный профиль — метаданные; он не включает автоматически проверки
  сценария, monetization, SDK, рекламу или сохранения.
- Следующая фаза может читать активное назначение профиля и предоставлять
  **только read-only** отчёт об отличиях legacy Starter Kit/CEOS без их
  изменения.

## Acceptance criteria

1. Базовые существующие CLI и тесты PR #1–3 неизменны по поведению.
2. Тесты: apply в non-empty game; preview нулевых побочных эффектов;
   повторный apply = `IN_SYNC`; upgrade с увеличенной версией; downgrade,
   same-version/source-drift и неподходящий engine/targets блокируются.
3. Пользовательские изменения и коллизии (в том числе symlink, junction,
   swap директории, гонки записи) сохраняются без потерь; сломанный или
   подменённый state не даёт обхода ownership.
4. При исключении до commit-point предыдущая активная ревизия сохраняется;
   прерванное обновление не оставляет активной полуревизии. Ошибка очистки
   после commit-point не удаляет подтверждённые зависимости.
5. Node.js 22/24, Windows-пути, `npm test`, `npm run check`,
   `node examples/core-session.mjs`; GitHub CI — PASS по фактическим логам.
6. Документация даёт команды для dry-run, apply, status и конфликтов.
   Release, runtime/host-parity и обновление файлов legacy игр не объявляются
   готовыми без отдельной проверки.

## Оставлено реализации

- Выделить маленький модуль profile-management в `packages/studio/src/`,
  подключить CLI и тесты без изменений Core и runtime.
- Выбрать компактный строгий JSON-schema state и детерминированную
  сериализацию, проверять собственные SHA-256/инварианты версий.
- Проверить безопасное атомарное переключение указателя на Windows и
  recovery при ошибках; документировать исключения по файловым системам.
